  `npm link` fait du binaire global la porte d'entrée (create app), sans risque de piloter une app
  avec une autre version que la sienne.
- **Complétion + `-v`** (`29ddc497`) : les built-ins viennent désormais du CODE (le cache ne porte
  que les commandes de module) ; `-v` rejoint la famille standalone (0 kernel, 0 log).

  alternatives rejetées) → **lot 1** briques framework (`fa448f42`) → **lot 2** le scaffold
  (`6d9643ab`) → **lot 4** docs + 2 fixes (`f2197e6c`) → **schéma WordPress** (`6e0205bd`) → recette

- Briques nées avec : décorateur **`@entities([...])`** + `defineEntity` (une app n'avait AUCUN point

## Coûts évidents

- **5 bugs framework/scaffold trouvés en EXÉCUTANT le code généré**, aucun visible côté générateur
  (85 tests verts). Le plus cher : `@HttpCode(204) + return null` pendait jusqu'au timeout.
- Le schéma WordPress (12 tables) a déclenché à lui seul 3 de ces 5 bugs — nos exemples maison ne les
  atteignaient pas (ils avaient toujours des horodatages après le dernier champ).
- 2 bugs signalés par le USER en usage réel (complétion sans `module`, 2ᵉ entité qui casse le build)
  — donc 2 trous de test de mon côté, comblés.

## Recommandations

1. **Gate d'un scaffold = le code généré** (typecheck de l'app + boot + CRUD réel + tests générés),
   jamais les seuls tests du moteur. → gravé dans RETEX (§ app générée).
2. **Renommage `IEntity.orm` → `connector`** (38 fichiers) **avant publication npm** — deux noms pour
   un concept ont déjà produit un bug silencieux.
3. Un cache sans invalidation ment pour toujours : ne jamais y mettre ce que le code sait dire.
