## Ce que la séance a appris

### Le rouge CI n'était pas « la case macOS » — le source de vite l'a dit en trente secondes

Le journal du job Windows donnait la piste que personne n'avait lue : les cinq autres cas du
fichier tenaient en **300 à 700 ms**, le cas litigieux était tué à **60 008 ms**. Ce n'est pas de la
lenteur, c'est un blocage. Le budget de repli du superviseur vaut
`(portRetryAttempts + 1) × startupTimeoutMs` = **80 s**, quand `testTimeout` vaut 60 s.

La cause du repli inutile est dans `httpServerStart` (vite 8.3.0) : trois textes contiennent
« in use », un seul est un échec.

| Texte de vite                                 | Ce que vite fait              |
| --------------------------------------------- | ----------------------------- |
| `Port X is **already** in use`                | `throw` — il MEURT            |
| `Port X is in use, trying another one…`       | `info` — il se décale         |
| `Port X is in use **on a wildcard address**…` | `warn` sur un `listen` RÉUSSI |

`isPortInUseMessage` rendait `already` OPTIONNEL : il prenait les trois pour un conflit. Via
`startupTimeoutMessage`, un démarrage qui avait seulement AVERTI puis dépassé l'échéance ressortait
en `EADDRINUSE:` — donc repli, donc une échéance de plus, quatre fois.

### Un test gravait la supposition

Le banc portait un cas « la formulation SANS `already` (versions antérieures) ». Parenthèse jamais
vérifiée : les trois textes coexistent dans la MÊME version. Le cas vert protégeait le défaut.

### Le repli qui ment, et le consommateur qui s'en défend

`status().port` rendait `resolvedPort ?? devPort` — une espérance servie pour un fait, en
contredisant son propre type (`number | null`). Une 2ᵉ application sans port résolu annonçait le
port de la première. **Le défaut était connu** : `FrontendService.cspPorts` portait un `⚠️` qui le
décrivait, et le contournait sur place. Un contournement documenté chez un lecteur est un défaut
non corrigé chez l'auteur.

## Coûts évidents
