# Session retro — 2026-08-25 — 441d2383

## Focus

Écrire le workflow d'intégration continue qui GÉNÈRE une application et l'ÉPROUVE
sur `ubuntu · macos · windows`. Puis, à la demande du user, auditer l'outillage
de développement d'une application générée et lui donner un vrai jeu de tests.

## Fait

- **`scaffold.yml`** — matrice 3 systèmes sur le plancher `engines` + une variante
  haute, décor ISOLÉ (tarballs hors dépôt), artefacts en échec. Vu MORDRE avant
  d'être cru : erreur de type injectée dans un gabarit, débranchement prouvé au
  `git diff --stat`, sortie 1 propagée à travers `| tee` sous `pipefail`.
- **La passe principale était rouge depuis 20 exécutions** — réparée (2 erreurs de
  lint, 1 fichier dérivé du formateur, 1 faux positif du gate `skills:check` qui
  classait deux RENDEURS de rapports en « bancs » sur du vocabulaire).
  Non-régression prouvée en rendant le site ENTIER avant/après : `diff -rq` identique.
- **Banc de conformité** (`verify-runtime.mjs`) — 51 cas, trois étages joués
  séparément : unitaire (18, aucun décor), intégration (13, l'app boote en entier
  sans ouvrir un port, via `nodefony inspect`), e2e (20, serveur réel en
  production). Vert en CI sur ubuntu ×2 et macOS. Les suites vivent dans le skill
  et sont INJECTÉES dans l'app témoin — jamais livrées à l'utilisateur.
- **Quatre défauts trouvés par ce workflow, et par lui seul** — Windows passé de
  0/13 à 12/13 : graphe symbolique gitignoré absent de tout checkout frais ·
  `npm` inexécutable sans shell · `oxlint.cmd` que « absolu » ne rend pas
  exécutable · 🔴 **la suite e2e de TOUTE application générée, morte sous
  Windows** — le seul qui atteignait les utilisateurs.
- **`nodefonyBin()`** publié par `nodefony/testing`, sur objection du user : le
  framework résout son propre lanceur, plus aucun chemin deviné chez l'utilisateur.
- Audit d'outillage de l'app générée : 8 écarts relevés sur pièces, 1 corrigé de
  ma part (les hooks git EXISTENT, ils sont seulement en opt-in).
- Actions Pages montées v4 → v5 (contenu de la PR Dependabot #12).

## Coûts évidents

- **Session très longue, en trois vagues** (workflow → audit → set de tests), là
  où la règle d'hygiène dit « une feature, une session courte ». Les deux
  extensions sont venues du user en cours de route, mais rien ne les obligeait à
  tenir dans la même session.
- **Sept relances du banc de conformité** pour stabiliser mes propres sondes —
  chacune ~30 s à 2 min. Le coût réel n'est pas là : c'est que dix des onze
  premiers rouges accusaient le produit à tort.
- Trois allers-retours CI pour Windows, chacun ~12 min d'attente. Incompressible :
  aucune machine du projet ne peut jouer ce verdict.

## Recommandations

1. **Regarder `gh run list` en OUVERTURE** de toute session qui touche à la forge.
   Vingt exécutions rouges d'affilée sans que personne ne le sache, c'est une
   information gratuite qu'aucune lecture de code ne donne.
2. **Une sonde neuve qui accuse massivement a tort d'abord.** Onze rouges, un seul
   vrai. Se demander « qu'est-ce que je viens de mesurer ? » avant « qu'est-ce que
   le produit a cassé ? ».
3. **Lire la colonne des DURÉES d'une suite verte.** Quinze cas à 0 ms n'ont émis
   aucune requête — le total ne le dira jamais.
