1. **« tu inventes alors, c'est pas sérieux »** — j'avais expliqué son erreur
   `request.body` depuis le framework, sans ouvrir `tmp/bench/appalpha`, dont
   **j'avais écrit le controller**. Le code y était faux au runtime aussi.
2. **« je me demande comment les tests de charge multi-pod ont marché »** — la
   bonne question. Réponse vérifiée : les bancs tapent `/burst` (qui lit
   `query`, peuplé) et `latency.mjs` poste sans corps → le chemin cassé n'a
   jamais été traversé. Les mesures tiennent.
3. **« tu as lancé la non-régression ? » / « tu es sûr de la perf ? »** — non
   aux deux : je m'étais arrêté aux tests unitaires et à un raisonnement.
   Lancées ensuite (587 intégration, gate mémoire 9/9), et la vérification a
   révélé que le banc d'intégration **ne prouvait pas** le changement.

## Recommandations

1. **Ouvrir le fichier dont parle le user avant de répondre** — même quand on
   croit connaître la cause, surtout quand on a écrit le code en question.
2. **Un test qui passe du premier coup sur un changement de comportement est
   suspect** — le banc apikey passait avec le défaut ET sans.
3. **Le filet manquant du motif « réglage sans lecteur »** : avertir au boot
   quand une app pose une clé `reserved`. `reserved` ne fait que griser dans
   Studio ; le kernel sait déjà prévenir pour un chemin env inconnu — c'est le
   pendant exact. Demande un accès générique au schéma depuis le cœur.
