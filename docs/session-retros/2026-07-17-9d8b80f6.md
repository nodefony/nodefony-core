## Ce que le diagnostic ne voyait pas

Le kit annonçait **5 cas mécaniques sur drizzle**. Terrain : **9 cas, sur 2 adapters**, dont
**1 faux positif**.

- `MongooseTokenStore` portait **exactement les mêmes** défauts (Lot 1 compris) — le kit ne parlait

- `DrizzleTokenStore.put` **n'était pas en danger** : les 3 appelants posent un id `randomUUID` →
  deux `put` du même id absent sont inatteignables. Le fix reste (1 round-trip au lieu de 2) mais son
  gain est la perf, pas la correction.
- `revoke` **l'était vraiment** : sans le `IS NULL` au WHERE, la 2ᵉ révocation écrase la 1ʳᵉ → l'audit

## Frictions (→ RETEX.md)

- **Un pool FROID masque les races** : test PG vert SANS le fix, 3/3, structurel. Le 1ᵉʳ écrivain
  (seule connexion chaude) finit avant que les autres aient leur TCP+auth. Sonde d'entrelacement pour
  le voir, `Promise.all` de `count()` pour chauffer.
- **`ON CONFLICT (x)` n'arbitre qu'UN index** : `access_token` a 2 uniques → le perdant lève en PG,
  passe en sqlite (divergence). Reproduit en **SQL pur** pour écarter notre code.
- **MySQL : ni RETURNING ni WHERE sur ODKU** → le design « clause `where` » du kit aurait coûté 2-3
  requêtes, donc une course. D'où `$max` (condition dans la valeur) = 1 instruction sur 4 backends.
- **Un test gaté par une variable d'env est un test qui n'existe pas** : `npm test` ne teste aucun
  dialecte réel (119 skipped en silence) ; le `RedisTokenStore` sur Redis réel n'avait **jamais**
  tourné.
- **« Consommé en source » = les TYPES seulement** : sans rebuild d'orm-core, `isFieldOperators`
  (runtime, donc `dist`) ignorait `$null` → `RangeError: Too few parameter values`, message qui ne
  parle pas du problème.
- Rappels qui ont mordu (déjà gradués) : **cwd Bash dérive** (2× — 783 tests `security` pris pour
  drizzle), `preserveModules` → ne pas grepper le seul `index.js`.

## Méthode qui a payé

Test **AVANT** fix pour chacun des 9 : la race est prouvée (message d'erreur réel), jamais supposée.
Deux tests ont dû être **réécrits parce qu'ils ne discriminaient pas** (assertion trop laxiste, pool
froid) — un test de concurrence qui ne rougit pas sans le fix ne teste rien. Et vérification en SQL
pur, hors framework, avant de choisir le design.

## Temps 2 — les stores sur les 3 dialectes (la dette du matin, soldée le soir)

Chaque store avait **deux** suites (une sqlite, une postgres) testant les mêmes invariants avec des
mots différents, et **aucune** sur mysql. Remplacées par un **banc partagé par store** (pattern
`repository-contract` : 1 banc + des consommateurs de ~20 l), joué sur les 3 dialectes.

**Le premier run mysql a sorti 2 bugs en 2 minutes**, invisibles depuis des mois :

- **`put` ÉCRASE le jeton légitime** sur collision de `secretHash` — `ON DUPLICATE KEY UPDATE`
  n'accepte pas de `target` → MySQL arbitre sur TOUTES les uniques (sqlite/pg REJETTENT). Reproduit
  en SQL pur, hors framework.
- **`signCount` en int32, spec W3C uint32** — pg `22003`, mysql `ER_WARN_DATA_OUT_OF_RANGE`, sqlite
  passe (INTEGER 64-bit).

Les deux sont des **divergences** → hors banc de parité (le banc teste l'identique). La règle
portable y reste, la divergence est gravée + testée des DEUX côtés, et documentée au dashboard.
Inatteignables en pratique → documentés plutôt que corrigés au prix d'un round-trip sur un chemin
chaud.
