# Session retro — 2026-08-29 — 0ad96a0b

## Focus

Reprise sur une forge rouge depuis cinq passes. Réparation, puis #98 (le `hint`), puis un audit
adverse de la conception des migrations qui a rendu trois défauts — tous confirmés ligne à ligne,
tous corrigés, tous éprouvés sur un pod réel.

## Fait

- **La forge d'abord.** Le banc de coupure portait trois défauts : décor jamais migré (il passait
  ici parce que la base d'un poste de développement traîne les tables d'une session en `auto`),
  sonde qui accusait le port pour une table absente, et surtout **aucune exigence de mise en
  service** — corrigé des deux premiers, il redevenait vert avec la migration DÉBRANCHÉE.
- **#98 (c)** — `isSchemaMismatch` et le champ `hint`, avec deux abstentions assumées : jamais en
  production (cartographie de schéma), jamais sur sqlite (`SQLITE_ERROR` générique).
- **Audit adverse (`fable`) + inventaire (`haiku`)** lancés en parallèle. Trois constats sérieux,
  vérifiés MOI-MÊME avant d'agir. L'inventaire a confirmé ses quatre ancrages ; son classement
  « le plus exposé » était en revanche une déduction non vérifiée, écartée.
- **#108** — un pod dont la base est en avance ne doit pas être retenu ; **#110** — publier un état
  n'est pas retenir le trafic ; **#111** — une clé déclarée sans défaut doit être surchargeable ;
  **#109** — honorer le refus des tables du framework.
- **`db-readiness-pod.mjs`** : trois scènes sur un vrai PostgreSQL et un vrai pod, contrôle négatif
  compris, câblé dans la forge.
- **Octet NUL** dans deux sources + son gate.

## Coûts évidents

- **Deux dérives de répertoire courant** (`cd` relatif dans un bloc, puis `cd` avalé par un
  heredoc Python) → deux « no tests » lus comme des échecs. Règle déjà graduée, geste pas acquis.
- **Trois refus du gate d'outillage** sur le même commit, dont un causé par prettier reformatant
  la ligne que je venais d'ajouter.
- **Deux assertions Python fautives** ont laissé un fichier écrit et l'autre non — état incohérent
  rattrapé à la main. Un script d'édition multi-fichiers doit vérifier AVANT d'écrire quoi que ce soit.
- **Une attente en arrière-plan sortie sur un faux signal** (`conclusion == null` vs chaîne vide).
- Serveur de développement arrêté/relancé trois fois (le garde d'instance unique refuse le mode
  production) — inévitable pour les bancs de pod, mais à annoncer.

## Recommandations

1. `causeProbable` dans le socle des bancs — déjà fait ; l'étendre aux autres bancs qui diagnostiquent
   un boot raté.
2. Un banc de pod exige que rien ne tourne : le dire dans le `SKILL.md` du banc plutôt que de le
   redécouvrir.
3. Vérifier `Kernel.ts:1691` — dernier appel non gardé à `configSchema()`.
