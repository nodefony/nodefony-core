## Le fait qui gouverne

**Les deux seuls défauts réels ont été trouvés en EXÉCUTANT, jamais en relisant.**

1. La chaîne semait un mot de passe d'administration aléatoire ; la suite e2e se connecte avec la
   constante de son décor. Le serveur tourne AILLEURS — dans un conteneur — donc la suite ne peut
   pas lui poser son identité. Résultat : un `401` que le cas imputait au proxy.
2. Un seuil bloquant sur CRITICAL rendait le job rouge pour toujours (`will_not_fix`).

Aucune assertion sur une chaîne de caractères n'aurait vu l'un ou l'autre. C'est exactement ce que
le ticket annonçait, et c'est le seul argument qui justifie de REJOUER un workflow au lieu de le
relire.

## Coûts évidents

- **Une app de test régénérée par le mauvais binaire.** `create app --force --dir` sur une app
  existante rend PARTIELLEMENT, avec les gabarits du `nodefony` **installé** (alpha.6) et non ceux
  du dépôt : Dockerfile `node:24-slim` au lieu d'`alpine`, `ci.yml` tronqué, `production.yml`
  absent. J'ai mesuré « 4 vulnérabilités critiques » sur une image Debian en croyant juger le
  gabarit courant. Rejoué sur une app neuve : 0 critique.
- **Décor sale** : le compte admin survit dans le volume `demo-var` avec l'ancien mot de passe (le
  semis est idempotent, il ne réaligne jamais). Un `down -v` manquant = un rouge qui accuse le
  produit. Le banc du dépôt documente ce piège — je l'ai repayé.
- **Mon exécuteur de workflow ne résolvait pas `${{ env.X }}`** : cinq cas e2e rouges sur une URL
  littérale. L'instrument, pas le produit.

## Recommandations

1. Le mini-exécuteur de workflow (`run-job.mjs`, jeté avec le scratchpad) mériterait de vivre dans
   le dépôt : rejouer un job GitHub en local a trouvé deux défauts en une séance.
2. `create app --force` sur une app existante devrait DIRE qu'il régénère depuis le paquet
   installé — le silence a coûté une mesure fausse.
