Pour qu'un framework comme Nodefony soit nativement et parfaitement "compatible Docker" (on dit souvent Cloud-Native), il ne suffit pas de lui ajouter un fichier Dockerfile. Le cœur même de ton code TypeScript doit adopter certains comportements pour collaborer sainement avec le moteur de conteneurs.

Si ton framework ne respecte pas ces règles, tes conteneurs mettront du temps à s'arrêter, perdront des requêtes en route, ou masqueront les adresses IP des utilisateurs.

Voici la check-list architecturale absolue pour rendre Nodefony 100% Docker-native.

1. La gestion des signaux système (Le "Graceful Shutdown")
C'est le point le plus critique. Quand tu demandes à Docker d'arrêter un conteneur (via docker stop ou lors d'un déploiement en production), Docker envoie un signal au processus Node.js appelé SIGTERM.

Le problème : Par défaut, Node.js ignore un peu ce signal ou coupe tout violemment. Si un utilisateur était en train d'uploader un fichier ou qu'un agent IA était en train de générer une réponse, tout est brisé net.

La solution dans ton framework : Nodefony doit intercepter ce signal pour fermer les portes proprement. Il doit :

Arrêter d'accepter de nouvelles requêtes HTTP ou de nouvelles connexions WebSockets.

Attendre quelques secondes que les requêtes en cours se terminent (en utilisant ton context.signal validé en P1.3).

Fermer proprement les connexions Postgres, Mongoose et Redis.

Quitter avec le code process.exit(0).
le kernel a deja pas mal d evenement si il faut en ajouter au bon moment avec des nom specifique devops c'est mieux 


2. Faire confiance aux Proxies (La gestion des IP de confiance)
Dans l'univers Docker, ton application est presque toujours cachée derrière un reverse-proxy, un WAF (comme l'instance waf-proxy de ta stack), ou un Load Balancer Cloud (AWS, Cloudflare).

Le problème : Si ton framework lit naïvement request.socket.remoteAddress, il va croire que tous les utilisateurs ont la même adresse IP : celle du conteneur de ton proxy (ex: 172.18.0.2). C'est dramatique pour ton Firewall (P6.3) et tes logs.

La solution dans ton framework : Nodefony doit inspecter les en-têtes standard de proxy (comme X-Forwarded-For et X-Forwarded-Proto) pour retrouver la vraie IP d'origine du client. Cependant, pour éviter l'usurpation d'identité, il ne doit lire ces en-têtes que si l'IP du proxy fait partie d'une liste blanche de confiance configurée dans ton module security

3. Les indicateurs de santé (Healthchecks : Liveness et Readiness)
En production, l'orchestrateur (Docker ou Kubernetes) a besoin de savoir si ton conteneur est en vie et s'il est prêt à recevoir du trafic. Ton framework doit proposer deux routes techniques légères par défaut :

GET nodefony/healthz (Liveness) : Renvoie un statut 200 OK très simple. Si ton framework ne répond plus (boucle infinie, crash complet), Docker le détecte et redémarre le conteneur.

GET nodefony/readyz (Readiness) : Vérifie que Nodefony a fini de s'initialiser et que les connexions Postgres, Mongo et Redis sont opérationnelles. Tant que cette route ne renvoie pas 200, le proxy ne lui envoie aucun utilisateur.

4. Configuration exclusive par Variables d'Environnement
Un conteneur Docker est une boîte noire immuable. Tu ne vas pas modifier un fichier de configuration .json ou .yaml à l'intérieur du conteneur selon que tu es en dev, en staging ou en production.

La règle : Tout ce qui peut varier d'un environnement à l'autre doit être lu via process.env.

Dans ton framework : Tu dois créer un service de configuration robuste capable de fusionner une configuration par défaut écrite en TypeScript avec les variables d'environnement injectées dans Docker (avec un typage strict : convertir "true" en true ou "3000" en number).

5. Le piège de Node.js en Processus Principal (L'anti-pattern PID 1)
Dans Linux, le premier processus lancé (le PID 1) a la responsabilité de nettoyer les processus enfants "zombies". Si dans ton Dockerfile tu lances ton application directement avec CMD ["node", "dist/main.js"], Node.js va devenir le PID 1. Le problème, c'est que Node.js n'a pas été conçu pour gérer les responsabilités du système d'exploitation. Les signaux comme SIGTERM risquent d'être mal transmis.

La solution dans le framework / infrastructure : Il faut recommander l'utilisation d'un init-système ultra-léger dans le conteneur, comme tini. Il s'occupe d'être le PID 1 parfait et passe proprement les ordres à ton code Node.js.

Dans ton Dockerfile.dev, cela se traduit simplement par :

Dockerfile
# Installer tini
RUN apk add --no-cache tini
# Lancer tini qui va piloter node
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "dist/main.js"]

# Nodefony Development Infrastructure Specification

Tu es l'ingénieur système et l'architecte principal sur le framework Nodefony Core. Ton objectif est de générer le fichier `docker-compose.yml` parfait pour notre environnement Cloud-Native et d'adapter la logique de boot du framework pour ce nouvel environnement.



## 1. Objectifs de l'Infrastructure
- **Auto-suffisance :** Le dépôt `nodefony-core` intègre le framework et se lance comme sa propre application autonome.
- **Zéro Friction Cross-Platform :** Fonctionner de manière identique sur Mac (Docker Desktop), Linux et Windows (WSL2).
- **Performance Temps Réel Impeccable :** Le réseau doit être configuré pour supporter le streaming, les WebSockets et les connexions asynchrones des Agents IA sans latence artificielle ni coupure.

## 2. Spécifications du Réseau Docker (Bridge Layer)
Tu dois configurer un réseau personnalisé avec le driver `bridge`. 
- Le conteneur applicatif `nodefony-core` doit être interconnecté avec toutes les briques via ce réseau.
- Pour le temps réel (WebSockets), assure-toi que les ports requis ne souffrent d'aucun conflit de mapping. Le conteneur de l'application doit exposer le port HTTP/WS principal.
- Utilise des alias DNS internes clairs (`postgres`, `mongodb`, `redis`, `keycloak`, `opensearch` , haproxy , nginx) pour que le framework n'utilise JAMAIS `localhost` ou `127.0.0.1`.

## 3. Topologie de la Stack à Générer 
Génère le `docker-compose.yml` à la racine  il faut traiter les mot de pass ou peut etre nodefony le fera quand les briques seront faites (provider Env vault ...)
1. **postgres :** Derniere Version  (Persistance transactionnelle / Données structurées).
2. **mongodb :** Derniere Version  (Mémoire flexible des Agents IA / Contextes LLM).
3. **redis :** Derniere Version  avec option `--appendonly yes` (Gestion des états des sessions WebSockets actives et bus de synchronisation).
4. **keycloak :** Derniere Version  configuré en mode `start-dev`, connecté à l'instance Postgres pour son stockage, exposant le port `8080`.
5. **opensearch :** Derniere Version  avec `ENABLE_SECURITY=false` et RAM bridée à 512m (`OPENSEARCH_JAVA_OPTS`) pour préserver la machine hôte.
6. **nodefony-core :** L'application elle-même. Elle doit builder à partir d'un `Dockerfile` ou `Dockerfile.dev`, monter le répertoire courant `.` il faut que le HMR et tout fonction fait les bon point de montage que l on puisse travailer , et utiliser `tini` comme `ENTRYPOINT` (PID 1) pour assurer la transmission des signaux système.

## 4. Adaptation des "Skills" de Démarrage (Boot Workflow)
Tu dois ameliorer le Kernel et la phase de démarrage (`HttpKernel` ) de Nodefony pour s'adapter à cet environnement conteneurisé :
- **Configuration Dynamique :** Remplace les configurations en dur par des appels au service `SecretProvider`  via `process.env` quand il sera developpé.
- **Validation Active des Connexions (Readiness) :** Au démarrage, le framework ne doit pas planter bêtement si une base de données met 2 secondes de plus à s'allumer. Implémente une logique de *Retry* (ex: 5 tentatives d'authentification espacées de 2 secondes) pour Postgres, Mongo et Redis avant de déclarer un échec critique.
- **Headers de Proxy :** Configure le serveur HTTP pour faire confiance aux en-têtes `X-Forwarded-For` et `X-Forwarded-Proto` si le trafic provient du réseau Docker.

## 5. Capacités d'Auto-Débuggage pour Claude Code
Le framework doit exposer des hooks de diagnostic pour que toi, Claude Code, tu puisses t'auto-débugger en utilisant ton **Docker MCP Toolkit** :
- **Logs Structurés :** En mode `development`, Nodefony doit écrire ses logs  pour que tu puisses les inspecter via la commande MCP `docker logs`.
- **Endpoints de Diagnostic :** Le framework doit activer les routes `/healthz` (Liveness) et `/readyz` (Readiness) qui renvoient l'état exact des connexions (vert/rouge) avec les détails de l'erreur si une brique lâche.
